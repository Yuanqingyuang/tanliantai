## 三、NUMERIC 精度

测试表：`amount numeric(18,6)`（整数位最多 12 位）。

| 用例 | 写入值 | 读出值 | 判定 |
| --- | --- | --- | --- |
| 最小小数 | `0.000001` | `0.000001` | 通过 |
| 最大合法值 | `999999999999.999999` | 同值 | 通过 |
| 负数边界 | `-123456789012.123456` | 同值 | 通过 |
| 六位舍入 | `1.0000005` | `1.000001` | 通过 |
| 超范围 | `1234567890123.000000` | 报错 `numeric field overflow` | 通过 |

累加对照：

| 方式 | 结果 |
| --- | --- |
| PostgreSQL `sum(numeric)`，十次 0.1 | `1.000000` |
| Python 浮点逐次累加，十次 0.1 | `0.9999999999999999`，与 1 的差为 `1.1102230246251565E-16` |

CSV 导出保持六位小数原样（`0.000001`、`1.000001`、`0.100000`），未出现科学计数法或精度丢失。

## 四、JSONB 快照

使用一条合成核算快照（含 `meta`、3 条 `items`、`totals`），验证结果：

| 检查 | 结果 |
| --- | --- |
| 写入嵌套结构 | 成功 |
| 按字段查询 `#>> '{meta,line}'` | 返回 `SMT-A` |
| 包含查询 `@>` | 命中 |
| 数组长度 | 3 |
| JSONB 内数值求和（0.1 + 0.2） | `0.3`（按精确数值，不是浮点近似） |
| 读出后指纹复算 | 前后一致：`f28f1ed81fe6…b4e42f` |
| 单条 JSONB 字节数 | 563 |
| 同一内容的文本形式 | 443 字节 |
| 表总占用 | 32 KB（含索引与页对齐） |

结论：JSONB 可作为不可变核算快照的存储形态，指纹在写入—读出链路保持稳定。

## 七、本地模型

测试方式：`model_bench.py` 跑 100 条**合成文本**，CPU 推理、fp32 未量化；模型权重不进仓库。同一台机器上先测 BGE-M3，再测 m3e，测量期间三个数据库容器已停止。

| 指标 | 阈值 | BGE-M3（候选） | m3e-base（回退） |
| --- | --- | --- | --- |
| 模型体积（磁盘） | 记录 | 2191.1 MB | 390.7 MB |
| 加载耗时（torch 已就绪） | 记录 | 2.617 s | 0.615 s |
| 单条编码延迟（中位 / p95 / 最大） | ≤ 500 ms | 122.9 / 161.7 / 409.3 ms | 36.1 / 40.6 / 45.4 ms |
| 单条检索延迟（编码 + 余弦） | 记录 | 约 123 ms | 约 36 ms |
| 进程内存峰值 | ≤ 2.5 GB | 1.870 GB | 0.800 GB |
| 冷启动（解释器 + 库导入 + 模型 + 首次编码） | ≤ 10 s | 11.086 s（复测 12.331 s） | 8.831 s |
| 判定 | — | 编码、内存达标；**冷启动不达标** | 全部达标 |

说明：

- 内存峰值为进程 RSS（含 torch 运行时），模型权重以 mmap 方式载入，RSS 低于权重文件体积属正常。
- BGE-M3 的冷启动 11.1–12.3 s 稳定超过 10 s，主要耗在 Python 与 torch 导入（约 8–9 s），模型本身加载仅 2.3–2.6 s。
- 两者对合成文本的 top-1 分布相同（模板关键词明显），这只是接口连通性证据，**不是召回率结论**；BGE-M3 与 m3e 的召回差异留给 T-0024 检索实验量化。
- 本机不是基准机，数字只作备注；阈值判定以基准机复测为准【待确认：确认人袁青扬】。

## 八、AIProvider 三态

实现见 [ai_provider.py](../../environment/spike/scripts/ai_provider.py)，由 `AI_PROVIDER` 环境变量切换。接口只返回**候选、依据、置信度与模型元信息**，不返回任何核算数值（规则 R2）；置信度仅用于排序。

| 实现 | 依赖 | 本次状态 | 延迟 | 说明 |
| --- | --- | --- | --- | --- |
| `mock` | 无（仅标准库） | ok | 0.038 ms | 确定性关键词匹配，同一输入重复运行结果一致 |
| `local`（BGE-M3） | sentence-transformers + 2.19 GB 权重 | ok | 首次 644.2 ms；稳定后约 123 ms | 首次含 9 条标签向量建索引；含 torch 导入的加载耗时 9.577 s |
| `local`（m3e-base） | 同上，390.7 MB 权重 | ok | 首次 113.8 ms | 回退候选，路径与参数不变 |
| `cloud` | OpenAI 兼容接口 + 密钥 | unavailable | 0.002 ms | 未配置 `AI_CLOUD_BASE_URL` / `AI_CLOUD_API_KEY` 时显式不可用，不静默降级到 mock |

结论：三态切换机制可用，同一份调用代码只靠环境变量即可换实现；未配置或加载失败时返回 `unavailable` 与原因字符串，避免"看起来能用"的假阳性。`cloud` 因缺少测试密钥，本次只验证了失败路径【待确认：确认人袁青扬】。

## 九、回退方案

- PostgreSQL：若 17.11 未被采纳，可直接回退 16.15；三版本测试均通过，回退不涉及数据迁移成本（阶段一尚无数据）。
- 本地模型：BGE-M3 在本机冷启动 11.1–12.3 s，超过 10 s 阈值，**建议默认锁定 m3e-base**（三项全部达标，体积 390.7 MB）；BGE-M3 仅在基准机复测达标或采用延迟加载（模型移出启动路径、首次检索时后台预热）后作为可选项。
- 代价：m3e-base 与 BGE-M3 的召回率差异尚未量化，需在 T-0024 检索实验中测定，本报告不预设数值。

## 十、复现步骤

```powershell
# 数据库：三版本同时启动
docker compose -f environment/spike/docker-compose.yml up -d

# 对 5433 / 5434 / 5435 各跑一次，对应 16 / 17 / 18
python environment/spike/scripts/db_checks.py --dsn "host=127.0.0.1 port=5433 user=postgres password=spike_local_only dbname=spike"

# AIProvider 三态
python environment/spike/scripts/ai_provider.py --compare --text "回流焊炉后做外观检查"

# 本地模型：先装依赖并下载权重（权重不进仓库）
pip install -r environment/spike/requirements-model.txt
modelscope download --model BAAI/bge-m3 --local_dir D:\models\bge-m3
python environment/spike/scripts/model_bench.py --model-dir D:\models\bge-m3 --label bge-m3

# 清理
docker compose -f environment/spike/docker-compose.yml down -v
```

清空卷重建已在 2026-11-02 本机验证：`down -v` 删除三个数据卷后按 compose 重建，三实例均转为 healthy，5433 全量测试再次 `pass=true`（结果见 `results/pg16-clean.json`，未入库）。**换一台机器从零启动**仍需确认人在另一台机器上照 README 执行，本报告不代替该步骤。
