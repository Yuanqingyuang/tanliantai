# 设计决策记录（ADR）

> 状态：首期骨架
> 子目录：关键设计决策记录

本目录用 ADR（Architecture Decision Record）记录**影响面大、改起来贵**的决策，避免同类问题反复讨论，也方便答辩与结题时说明"为什么这么做"。

## 一、什么时候必须写 ADR

- 技术栈选型：语言、框架、数据库、打包与部署方式。
- `app/` 形态：桌面应用外壳 vs Web 工作台，以及本地部署与数据出域边界。
- 核算口径：系统边界、功能单位、分摊方法基线的确定与变更。
- 数据契约的破坏性变更：字段、单位、数据包格式的版本跃迁。
- 测试基准（`tests/fixtures/`）的基线变更。
- 任何"两个方案都可行但只能选一个"的取舍。

不需要 ADR：措辞调整、格式修正、补齐已有的确定事项。

## 二、文件命名与模板

```text
NNNN-短横线小写英文标题.md     例：0001-deterministic-calculation-vs-ai-copilot.md
```

每份 ADR 使用以下结构（直接复制下方模板）：

```markdown
# NNNN. 决策标题
> 状态：提议 / 已接受 / 已废弃 / 被 NNNN 取代
> 日期：YYYY-MM-DD
> 决策人：…（含复核人）

## 背景与问题
## 备选方案（≥2 个，各写优劣）
## 决策
## 理由
## 后果与代价
## 影响范围（目录、契约、模块）
## 复核与重审条件
```

## 五、维护规则

- ADR 一经"已接受"不得修改正文结论；需要变更时新建 ADR 并在旧文件中标注"被 NNNN 取代"。
- 决策索引表必须与目录中的文件保持一致；新增 ADR 时同提交更新本表与 [CHANGELOG.md](../../CHANGELOG.md)。
- ADR 与 [架构文档](../architecture/README.md)、[契约清单](../../contracts/README.md) 冲突时，以已接受的 ADR 为准，并尽快修正另两处。
