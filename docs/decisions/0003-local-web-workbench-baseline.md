# 0003. 本地 Web 工作台技术基线：应用形态、技术栈、部署并发与模型运行

> 状态：已接受
> 日期：2026-10-27
> 决策人：项目团队（2026-10-27 讨论确认）｜复核：指导教师（复核意见待补录）
> 讨论记录：2026-10-27 确认 Web 客户端、Vue + TypeScript/Python、PostgreSQL、内网多用户、分阶段混合。

## 背景与问题

仓库目前处于文档与结构阶段，尚无代码。[架构文档](../architecture/README.md) 仍把整体技术栈、`app/` 形态和 AI 模型调用方式列为未决项；原计划书的技术基线是 Vue/TypeScript、Python/FastAPI、MySQL；外部技术稿则建议 PostgreSQL 与本地嵌入模型。三处说法不一致，导致任务无法稳定切分：前端、部署、认证、模型评测任务的影响目录和验收标准都依赖这四项决定。

本 ADR 只处理四个会改变任务边界的问题：

1. **应用形态**：Web 工作台还是桌面外壳。
2. **技术栈与数据库**：沿用 MySQL，还是切换到 PostgreSQL。
3. **部署与并发**：单机单用户，还是企业内网多用户。
4. **模型运行**：本地离线、云端接口，还是混合。

功能单位与系统边界、分摊方法、因子来源、数据包格式等核算与契约问题不在本 ADR 范围内，继续留在[待决策清单](README.md)。

## 备选方案

### A. 应用形态

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A1. Web 工作台 | 浏览器访问本机或内网的 FastAPI 服务，前后端分离 | 与计划书和 PPT 的"Web 工作台前端"一致；无需安装包；演示和联调成本低；后续可加壳 | 需要同时维护前端与后端进程；离线分发时要额外打包 |
| A2. 桌面外壳 | 用 Tauri 或 Electron 包住同一套 Web 界面 | 双击即用，文件访问方便 | 打包、签名、升级、崩溃排查都增加工作量；首期收益不明显 |
| A3. 纯桌面 | PySide/Qt 或类似框架重写界面 | 单进程、离线能力强 | 界面开发量大，无法复用 Web 生态，多用户与浏览器演示都更困难 |

### B. 技术栈与数据库

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| B1. Vue + FastAPI + PostgreSQL | TypeScript/Vue 3 前端，Python/FastAPI 后端，PostgreSQL 存实体、版本与快照 | `NUMERIC` 精确小数、`JSONB` 存结构化快照、后续可接 pgvector；单一后端语言 | 团队需要承担 PostgreSQL 的学习与运维；与原计划书基线不同 |
| B2. Vue + FastAPI + MySQL | 前端后端同 B1，数据库沿用 MySQL 8 | 与原计划书一致，团队更熟悉，迁移风险低 | `JSONB` 能力弱于 PostgreSQL；向量检索需要独立组件；未来换库成本更高 |
| B3. Django/DRF + React | 换成全家桶后端与另一套前端生态 | 生态成熟、后台管理现成 | 与"契约先行、模块化单体"的治理方式不匹配；团队现有积累用不上；首期负担过重 |

### C. 部署与并发

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| C1. 单机单用户 | 服务只监听本机回环地址，一个操作者使用 | 认证、权限、并发控制都可后置；最快跑通闭环；数据不出本机 | 无法直接支持多人协作与企业试点 |
| C2. 内网多用户 | 部署在企业内网，配置登录、角色与权限 | 更接近真实使用场景 | 需要用户/角色/审计/并发控制，MVP 范围明显扩大 |
| C3. 公网服务 | 部署到云上，多租户使用 | 访问方便、可演示 | 与企业数据不出门的约束冲突；安全与合规成本最高 |

### D. 模型运行

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| D1. 本地离线 | Sentence Transformers + 本地嵌入模型，随安装包预置 | 企业数据不出内网；演示不依赖网络；结果可重复 | 需要实测 CPU 内存与延迟；模型文件体积较大 |
| D2. 云端接口 | 调用外部模型 API | 无需本地算力，模型能力强 | 企业 BOM 与工艺数据出域，违反数据安全约束；离线演示不可用 |
| D3. 混合 | 敏感数据走本地，公开数据走云端 | 兼顾能力与合规 | 两套链路、两套评测，首期复杂度高 |

## 决策

**本 ADR 已接受，作为实施基线。** 后续如需改变结论，新建 ADR 并标注本文件“被 NNNN 取代”，不直接修改已接受的决策。

### A. 应用形态

采用 **A1：Web 客户端（浏览器工作台）**。浏览器访问本机或内网的 FastAPI 服务，前后端分离；首期不制作桌面安装包。若后续确需离线分发，再用 Tauri 或 Electron 包壳，不改变前后端结构。

### B. 技术栈与数据库

采用 **B1**：

- 前端：TypeScript、Vue 3、Vite、Element Plus、Vue Router、Pinia、Apache ECharts。
- 后端：Python 3.11 及以上、FastAPI、Pydantic v2、SQLAlchemy 2、Alembic。
- 数据库：PostgreSQL 16.x（评审时以经兼容性验证的稳定小版本为准）。
- 数值与文件：Python `Decimal` + PostgreSQL `NUMERIC` 承载正式数值；pandas、openpyxl 只走导入导出与非权威数据处理。
- 报告与测试：Jinja2、HTML；pytest、Hypothesis、Vitest、Playwright。
- 部署：Docker Compose，依赖版本与镜像摘要随首次集成锁定。

**不选 B2（MySQL）**：数据库确定为 PostgreSQL，团队接受其学习与运维成本；`JSONB`、`NUMERIC` 与后续 pgvector 的统一管理是选择理由。若 T-0010 验证证明 PostgreSQL 不可行，另立 ADR 重新决策，不在实现中混用两种数据库。不选 B3。

主理人已确认前端采用 Vue + TypeScript、后端采用 Python；FastAPI 与 PostgreSQL 是本 ADR 对语言选型的细化，仍需签注后生效。

### C. 部署与并发

采用 **C2：企业内网多用户**。服务部署在企业内网，浏览器访问，默认不开放公网。首期实现四类角色：项目管理员、数据录入者、核算复核者、只读查阅者；权限在服务端校验，按项目/模块控制，字段级细粒度权限后置。账号由管理员创建，不开放自助注册；密码使用哈希存储，登录使用服务端会话（HttpOnly Cookie），内网部署启用 HTTPS，并加登录限流与 CSRF 防护。登录、确认、导出和权限变更均留审计记录。

### D. 模型运行

采用 **D3：分阶段混合**，而不是一步到位的本地离线：

- **开发期**：先用云端模型 API 搭建简易 Agent，快速联调界面、候选流程与接口；只允许输入公开、合成或已脱敏数据，不得发送真实企业 BOM、工艺、能耗或供应商信息。
- **接口预留**：智能层统一走 `AIProvider` 适配接口（cloud / local / mock），业务代码不直接绑定某一家 API；切换提供方不改变候选输出契约。
- **交付与真实数据**：企业真实数据一律本地处理；本地模型（候选基线 BGE-M3 + Sentence Transformers）与离线资源包在阶段三至四完成，断网也能运行。
- **完整 Agent skill**：属于实现层的可复用能力包，不在本 ADR 决策范围；但必须遵守 R2（只出候选、不写正式核算输入）与人工确认接口，skill 的工具权限单独登记。

## 理由

- **A1**：计划书与 PPT 已经按 Web 工作台描述成员分工，选 A1 可以消除架构文档中"目录叫桌面外壳、分工写 Web"的矛盾；浏览器打印也满足可读报告的低成本输出。
- **B1**：后端统一在 Python，便于数据处理、实验与接口共用一套代码；FastAPI 的 OpenAPI 能直接支撑契约先行；`NUMERIC`/`Decimal` 满足"同输入同结果"的精度要求；`JSONB` 适合保存不可变快照。PostgreSQL 的风险主要集中在团队学习成本，因此用回退条款控制。
- **C2**：直接做内网多用户，避免单机版交付后再次补认证、权限和审计；权限管理在契约与最小集成阶段就落地，企业试点时不用推翻数据模型。代价是 MVP 范围扩大，需要单独的认证与权限任务。
- **D3**：云端 API 能把界面联调和候选流程先跑起来，本地模型则保证真实企业数据与离线交付合规。把差异收敛到 `AIProvider` 接口后，开发期与交付期可以共用同一套候选输出契约，避免后期重写业务逻辑。代价是两条链路都要配置与评测，这个成本必须提前计入。

## 后果与代价

- 需要同时维护 Node 与 Python 工具链，以及 PostgreSQL 容器；首次集成成本高于单文件脚本。
- 选择 PostgreSQL 的学习与运维成本已接受；若 T-0010 验证失败，会触发一次新的 ADR 决策，不再保留 MySQL 并行回退。
- 本地嵌入模型会占用内存并增加安装包体积；CPU 模式下的延迟尚未实测，不能当作已知条件。
- 开发期云端 API 会产生调用成本、网络依赖和供应商锁定风险；必须做 `AIProvider` 适配、超时与降级，不能把业务逻辑写死在某一家的 SDK 上。
- 云端与本地两条链路需要两套配置、两套评测；接口预留能降低返工，但不能消除这部分工作量。
- 数据边界必须由技术手段强制：请求字段白名单、脱敏、审计日志和真实数据标记缺一不可，不能只靠开发约定。
- 内网多用户意味着登录、角色、会话、CSRF、密码策略、审计和并发控制都进入 MVP；需要额外准备 HTTPS、账号管理和权限测试矩阵。
- 桌面安装包、自动更新、代码签名都不在本期范围；如果答辩要求"双击即用"，需要另立打包 ADR。

## 验证与重审条件

在阶段一结束前完成一项技术验证任务（见 WBS 的 T-0010），至少覆盖：

1. 云端模式：用合成或脱敏 BOM 跑通候选流程，抓包与日志确认没有真实敏感字段出域；
2. 本地模式：断网环境完成安装、启动、检索、候选、核算与数据包导出，并记录 Top-3、单条延迟与峰值内存；
3. provider 切换：同一输入在 cloud / local / mock 三种提供方下候选格式一致，正式数值不依赖模型；
4. 用一条完整核算快照验证 PostgreSQL `JSONB` 的写入、读出与指纹复算；
5. 记录 Node、Python、PostgreSQL 与模型的实际版本，形成锁定清单；
6. 权限矩阵：管理员、录入者、复核者、只读四类角色逐项验证，越权访问被拒，登录、确认、导出与权限变更有审计记录。

出现以下情况时重审本 ADR：

- 团队评审认定 PostgreSQL 的迁移或运维成本不可接受，或验证任务无法在阶段一内完成；
- 云端服务条款无法关闭训练或留存，或无法满足数据不落地的要求；
- 本地模型在目标机器上的延迟或内存不可接受，离线资源包无法交付；
- CPU 检索延迟或内存超出可接受范围，需要换更小模型或调整硬件基线；若改用云端，只能处理非敏感数据；
- 需要公网访问、多租户或 SSO；
- 答辩或交付要求桌面安装包；
- 模型或依赖的许可证不允许预期分发方式。

重审时新建 ADR 并在本文件标注"被 NNNN 取代"，不直接修改已接受的结论。
