# 策略：协作

> 状态：草案

适用：人（项目负责人、模块负责人、指导教师）与 Agent 之间的日常协作。目标是在无专职文档与配置管理角色的团队里，仍然保持"结论有依据、改动可追溯、并行不打架"。

## 1. 人对 Agent 的指令要求

一份可执行的指令至少包含：

| 项 | 要求 | 缺失后果 |
| --- | --- | --- |
| 目标 | 要达成什么结果，可判定 | Agent 会自行扩大或缩小范围 |
| 范围与非目标 | 明确不做什么 | 越界改动风险 |
| 输入资料 | 指向具体文件或登记表条目 | Agent 只能猜测口径 |
| 验收标准 | 可观测的判定条件 | 交付无法验收 |
| 影响目录 | 允许改动的目录清单 | 触碰禁止区 |
| 测试要求 | 需要哪一层测试与证据 | 交付不可复核 |
| 确认人 | 出现「待确认」时找谁 | 任务卡住或私自假设 |

推荐做法：直接用 [`templates/task.md`](../templates/task.md) 下发任务；指令中引用文件请用仓库相对路径。

## 2. Agent 对不确定性的处理

| 情形 | 处理方式 |
| --- | --- |
| 事实不明（数字、选型、口径） | 写「【待确认】」+ 需要谁确认，不编造（对应 `AGENTS.md` R1） |
| 关键依据缺失且阻塞 | 停止该分支，交付其余可完成部分，并明确列出阻塞点 |
| 规则冲突 | 以 `AGENTS.md` > `.agents/policies/` > `workflows/` > 其他文档 的顺序裁决，并回报冲突 |
| 任务类型不在 [`context-map.md`](../context-map.md) | 不猜测，请项目负责人确认任务归属 |
| 需要越界修改 | 按 [`boundaries.md`](boundaries.md) 第 6 节提报批准，不擅自推进 |
| 可能影响核算结果 | 一律按"有影响"处理，走 [`calculation-change.md`](../workflows/calculation-change.md) |

禁止行为：把不确定项写成断言；用"大概""应该是"替代依据；静默选择一个口径继续做。

## 3. 并行任务的文件分区

原则：**同一文件同一时间只有一个负责人**。

| 规则 | 说明 |
| --- | --- |
| 先分区再开工 | 并行任务在任务说明中列出各自独占的文件/目录清单 |
| 共享文件串行 | `knowledge/*`、`contracts/`、`tests/fixtures/` 等共享登记类文件串行修改，或由一人集中修改 |
| 契约优先 | 跨模块字段变更先由契约负责人落地，其他任务基于新契约实现 |
| 文档分区 | 不同文档由不同 Agent 负责，避免同文件并发编辑 |
| 分区冲突 | 发现他人正在同一文件工作时，停止并上报，不覆盖他人改动 |

参考分区（对应模块分工，具体以任务说明为准）：

| 模块方向 | 典型受影响目录 |
| --- | --- |
| BOM 语义解析与 AI 候选匹配 | 解析、候选与评测相关实现与文档 |
| 确定性核算引擎与资源分摊实验 | 核算层实现、公式登记、分摊实验记录 |
| 碳数据包与审计链、后端接口 | 数据包实现、[`contracts/`](../../contracts/README.md)、日志与权限 |
| Web 工作台前端与评测实验 | 界面实现、评测记录、[`docs/development/`](../../docs/development/README.md) |

## 4. 冲突处理

判定顺序（高优先级胜出）：

1. `AGENTS.md` 硬性规则
2. 已批准的 ADR（[`docs/decisions/README.md`](../../docs/decisions/README.md)）
3. `.agents/policies/`
4. `.agents/workflows/`
5. 其他文档与实现现状

处理步骤：

1. 记录冲突双方的文件与原文位置。
2. 判断是否涉及核算口径或数据安全：若涉及，升级给项目负责人与指导教师。
3. 给出建议裁决与影响，等待确认后再动手。
4. 裁决结果写回对应文件，避免同一冲突反复出现。

## 5. 交付报告要求

每次交付按 [`templates/delivery-report.md`](../templates/delivery-report.md) 输出，至少包含：

- 变更摘要（做了什么、为什么）
- 涉及文件（含路径与变更性质）
- 验证方式与结果（命令/步骤 + 实际结果，含失败与未执行项）
- 未决问题（「待确认」项 + 确认人）
- 下一步（建议的后续任务）

交付报告三条硬要求：

1. 不得声称未执行的验证为"已通过"。
2. 不得隐藏失败与越界。
3. 对核算相关改动，必须给出可复算的证据。

## 6. 沟通与留痕

- [ ] 关键决策（口径、选型、边界）必须有书面记录并落到仓库文件
- [ ] 口头结论需在交付报告中复述确认
- [ ] 人工确认必须留痕：确认人、确认对象、结论
- [ ] 重要变更同步到 `CHANGELOG.md`

## 7. 自检清单

- [ ] 我的任务说明包含目标/范围/非目标/验收标准/影响目录/测试要求
- [ ] 我未在他人负责的文件上并发修改
- [ ] 我的不确定性都以「待确认」呈现
- [ ] 我的交付报告如实反映了验证结果
