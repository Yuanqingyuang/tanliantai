# 策略：修改边界

> 状态：草案

目的：让 Agent 明确"能改什么、必须先问什么、绝对不能碰什么"。判定顺序为 禁止区 → ADR 区 → 受控区 → 自由区。对应 `AGENTS.md` 规则 R7。

## 1. 禁止改动（硬边界）

| 对象 | 禁止行为 | 原因 |
| --- | --- | --- |
| 企业真实数据 | 任何形式提交进 Git、写入示例、写入测试基准 | 数据安全底线（R4） |
| `knowledge/` 下因子的来源与版本字段 | 未登记即使用、改写来源、删除历史版本 | 破坏可追溯性与可复算性 |
| 基准数据的既有取值 | 为了让测试通过而直接改基准数值 | 使复算证据失效 |
| 审计留痕数据 | 删除或改写计算记录、候选记录、人工确认记录、访问日志 | 破坏可审计性 |
| 已冻结的对外材料 | 直接覆盖 | 结题与答辩材料需可复现 |

命中禁止区时的正确做法：停止改动，在交付报告中说明"为何需要、影响是什么、需要谁批准"，等待确认。

## 2. ADR 区（必须先写 ADR 才能改）

这些改动影响面广或不可逆，必须先有决策记录：

| 改动 | ADR 需回答 |
| --- | --- |
| 编程语言、框架、数据存储选型 | 目标场景、替代方案、放弃理由、迁移成本 |
| 桌面外壳 vs Web 工作台形态 | 部署条件、企业内网可用性、离线与本地部署要求 |
| 核心实体字段的破坏性变更 | 字段口径变化、旧数据兼容策略、版本号动作 |
| 结果指纹算法 | 为何需要变、历史指纹如何比对 |
| 系统边界与分摊方法 | 依据、影响的核算结果范围 |
| 数据包规范的破坏性变更 | 规范版本、迁移说明 |
| 目录结构重组 | 影响范围、链接与引用修复方案 |

ADR 归档于 [`docs/decisions/README.md`](../../docs/decisions/README.md)。ADR 未定前，实现中不得假设某种选型（需在代码与文档中标注「待确认」）。

## 3. 受控区（可改，但有强制配套动作）

| 目录 | 可做 | 强制配套 |
| --- | --- | --- |
| [`knowledge/formulas/`](../../knowledge/formulas/formula-register.md) | 新增/修订公式登记 | 走 [`calculation-change.md`](../workflows/calculation-change.md)，附依据与复算 |
| [`knowledge/emission-factors/`](../../knowledge/emission-factors/factor-register.md) | 新增/替换/淘汰因子 | 四重校验（来源/单位/区域/版本）+ 因子快照 |
| [`contracts/`](../../contracts/README.md) | 字段、类型、单位、必填性变更 | 契约先行：先改契约，后改实现，附迁移说明（R5） |
| [`tests/fixtures/`](../../tests/fixtures/README.md) | 新增基准案例、扩充覆盖 | 说明构造方式与预期结果；既有取值如需变更须给出独立理由与影响评估 |
| [`data/examples/`](../../data/examples/README.md) | 示例数据 | 必须脱敏；不得由真实数据"轻改"得到 |
| [`docs/architecture/`](../../docs/architecture/README.md) | 字段口径与结构说明 | 与 [`contracts/`](../../contracts/README.md) 同步，不得单边修改 |
| [`environment/`](../../environment/README.md)、[`tools/`](../../tools/README.md) | 环境与脚本 | 同步更新 README；自检脚本需通过 |

## 4. 自由区（在任务范围内可直接修改）

- 本次任务明确指定的实现与测试文件
- 新增文档的正文表述（不得引入未登记数字）
- 界面文案、排版、提示语（不改变口径含义）

## 5. 变更分级与必备动作

先给变更定级，再决定要走多少流程，避免"改一个错别字"与"改一条核算公式"付出同等成本。级别取**更高**者；判据不清时同理。

| 级别 | 判据（命中任一即该级） | 必备动作 |
| --- | --- | --- |
| T0 轻量 | 纯文案 / 排版 / 错别字 / 代码注释 / 无口径影响的界面文案 | 直接提交；免任务说明与交付报告；结构与链接检查仍须通过 |
| T1 常规 | 不触及口径、契约、基准的一般实现 / 文档 / 脚本 | 任务台账登记 + 交付报告 + CI 四门禁（`structure` / `data-safety` / `links` / `change-guard`） |
| T2 敏感 | 核算口径（公式 / 因子 / 边界 / 分摊）、契约、数据包格式、`tests/fixtures/` 基准数据，或任何破坏性变更 | T1 全部，另走 [workflows/calculation-change.md](../workflows/calculation-change.md)（口径类）与必要 ADR，并取得非作者签注（[workflows/review.md](../workflows/review.md) §7） |

- T0 同样不得触碰第 1 节禁止区；数据脱敏要求不因级别降低。
- 定级结果写入任务台账的「类型」与交付报告；定级错误按越界处理流程（第 7 节）纠正。

## 6. 基准数据（`tests/fixtures/`）特别规则

- [ ] 新增基准：说明数据来源（标准算例 / 脱敏真实结构 / 构造案例）与预期结果推导过程
- [ ] 修改既有基准取值：视为**核算口径级**变更，需独立理由、影响评估与人工确认
- [ ] 禁止用"更新基准期望值"的方式让失败用例变绿
- [ ] 基准数据必须可在无企业数据环境下独立运行

## 7. 越界处理流程

1. 停止改动，保留现场说明（改了哪些文件、为什么）。
2. 在交付报告中列为"需批准事项"，写明影响范围与风险。
3. 由项目负责人判断走 ADR、走核算变更流程，或终止该改动。
4. 未获批准前不得继续推进相关改动，也不得隐藏改动。

## 8. 自检清单

- [ ] 我改的每个文件都在任务说明的"影响目录"内
- [ ] 未触碰禁止区
- [ ] 涉及选型的改动已有 ADR 或已标注「待确认」
- [ ] 受控区改动已按配套流程完成登记
- [ ] 未修改基准数据取值来迁就实现
